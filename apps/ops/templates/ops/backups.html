Database backups

Superusers only. Snapshots include all database records: users and password hashes, sessions, API token hashes, encrypted settings, schedules, and application content.

Store downloads securely. Files, environment variables, encryption keys, and downloaded models are not included. Keep the same code revision, migrations, and encryption keys when restoring.

Snapshots can migrate data from SQLite to PostgreSQL or back when the schema and keys match. Automated exports take a consistent database snapshot and may briefly block writes.

Use a maintenance window for restores. Stop workers, Beat, and other database writers before restoring. For command-line restores, stop the web service too. Restart services after restoring to clear cached settings. For large databases, use native database backups.

Automated encrypted backups

Disabled by default. Choose a daily time and time zone, then a destination. Set BACKUP_ENCRYPTION_KEY in the environment of the web and worker services first. Keep that key separately: without it, encrypted backups cannot be restored. All backup files are retained; configure retention in your storage provider.

Celery Beat and a worker must be running. Local folders must already exist and be writable in the worker container (mount your drive there). External S3 requires HTTPS and permission to upload objects to the chosen bucket and prefix. Saved S3 credentials are encrypted and never displayed.

For bundled Silo, choose S3 storage, endpoint http://silo:9000, bucket kashengine-backups, and region us-east-1. Use a dedicated upload-only S3 access key, not the root login. Only this private endpoint is allowed over HTTP; backup files remain encrypted.
